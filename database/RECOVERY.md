# Резервные копии и восстановление StudHub

Инструкция для Windows, Docker Desktop и PostgreSQL 16. Все команды выполняются
из корня StudHub. Рабочую базу скрипты не удаляют и не перезаписывают.

## Что сохраняется

Одна папка копии содержит:

- `database.dump` — схема, таблицы, записи, связи, индексы и последовательности PostgreSQL;
- `two-factor.key` — действующий 32-байтовый ключ шифрования двухфакторной защиты;
- `manifest.json` — дата UTC, версия PostgreSQL, имя базы и SHA-256 обоих файлов;
- после проверки — `restore-check-*.json` с результатом восстановления.

В базе находятся аккаунты с хэшами паролей, курсы, задания, проекты, чаты,
настройки, фотографии профилей и другие данные, реально сохранённые в PostgreSQL.
Временные лекции AI и браузерные черновики в дамп не входят. `.env`, API-ключи,
пароль роли PostgreSQL и исходный код не копируются. Код хранится в GitHub,
доступы к внешним сервисам и пароль PostgreSQL — в вашем менеджере паролей.

**Копия содержит персональные данные и ключ 2FA.** Папка по умолчанию:
`%LOCALAPPDATA%\StudHub\backups` — вне проекта и OneDrive. Новая папка доступна
по NTFS только текущему пользователю Windows и SYSTEM. Это ограничение доступа,
а не шифрование архива. На другом носителе используйте BitLocker или другое
проверенное шифрование. Не отправляйте копии в GitHub, мессенджеры и публичное облако.
Контрольные суммы обнаруживают повреждение, но не доказывают подлинность:
восстанавливайте только свои доверенные копии.

## 1. Создать копию

1. Откройте Docker Desktop и дождитесь его готовности.
2. Запустите PostgreSQL (приложение для обычного копирования может работать):

```powershell
docker start studhub-db
```

3. Запустите скрипт:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\scripts\Backup-Postgres.ps1
```

`Bypass` действует только в запущенном процессе; политика Windows не изменяется.
При успехе последняя строка — полный путь к созданной папке. Сохраните этот путь.
Имена папок используют UTC, поэтому дата в имени может отличаться от местной.
Существующие копии не заменяются и автоматически не удаляются.

Скрипт работает через Docker и не зависит от внешнего порта 5432/15432.
Пароль не передаётся в командной строке: используется локальное соединение
внутри вашего контейнера. Если локальная политика PostgreSQL требует пароль,
настройте защищённый `.pgpass` в контейнере; скрипт не меняет `pg_hba.conf`.

Другие настройки при необходимости:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\scripts\Backup-Postgres.ps1 -Container studhub-db -Database studhub -User studhub -OutputRoot "D:\StudHubBackups"
```

Путь `D:` — только пример: выбирайте существующий защищённый NTFS-диск.
Ключ берётся из явно переданного `-KeyFile`, иначе из `STUDHUB_2FA_KEY`, иначе
из `STUDHUB_2FA_KEY_FILE` или `.studhub/security.key`. Запускайте копирование
с тем же ключом, что использует приложение. Если ключ задан в другом окружении,
передайте фактический файл через `-KeyFile`. Нельзя создавать новый ключ вместо
потерянного: он не расшифрует старые секреты 2FA.

`manifest.json` появляется последним. Если команда завершилась ошибкой,
не считайте папку готовой копией: устраните причину и создайте новую.

## 2. Проверить восстановление без риска для рабочей базы

```powershell
$backup = "ПОЛНЫЙ_ПУТЬ_К_ПАПКЕ_КОПИИ"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\scripts\Test-PostgresRestore.ps1 -BackupDirectory $backup
```

Будет создана новая база `studhub_restore_test_...`. Скрипт проверит контрольные
суммы, восстановит архив одной транзакцией и прочитает все таблицы. Выведет имя
тестовой базы и путь к отчёту. Тестовая база остаётся для проверки; автоматического
удаления баз нет. Наличие файла дампа само по себе не считается проверкой восстановления.

Для строгого сравнения с исходной базой:

1. Остановите StudHub и другие программы, которые записывают в эту базу.
2. Создайте **новую** копию при остановленных записях.
3. Выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\scripts\Test-PostgresRestore.ps1 -BackupDirectory $backup -CompareWithStoppedSource
```

Сравниваются количество и хэши строк каждой таблицы, столбцы, индексы,
последовательности, внешние/уникальные ключи. Для CHECK сравниваются имена,
столбцы и состояние проверки: PostgreSQL может записать эквивалентные приведения
типов иначе после восстановления. Для крупных баз проверка хэшей может потребовать
много памяти; текущий способ рассчитан на размер локального StudHub.
Если во время сравнения кто-то пишет в исходную базу, различие не обязательно
означает повреждение дампа — повторите проверку без записей.

## 3. Восстановиться после потери данных

1. Остановите приложение. Сохраните текущую базу отдельной копией, если она доступна.
2. На новом компьютере установите Docker Desktop, загрузите код StudHub той же
   версии и запустите PostgreSQL 16. Создайте роль подключения через настройки
   контейнера; сохраните её пароль отдельно от копий.
3. Выберите последнюю **проверенную** папку копии, включающую дамп, manifest и ключ.
4. Восстановите в новое имя:

```powershell
$backup = "ПОЛНЫЙ_ПУТЬ_К_ПАПКЕ_КОПИИ"
$restoredDb = "studhub_restore_recovered_20261116"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\database\scripts\Restore-Postgres.ps1 -BackupDirectory $backup -TargetDatabase $restoredDb
```

Если имя уже занято, выберите другое. Скрипт специально не содержит режима
перезаписи и не использует `--clean`. При ошибке восстановления новая пустая
база может остаться для диагностики; успешный результат не выводится.

5. Направьте приложение на восстановленную базу и **ключ из той же копии**:

```powershell
$dbPort = (docker port studhub-db 5432/tcp | Select-Object -First 1) -replace '^.*:', ''
$env:DB_URL = "jdbc:postgresql://127.0.0.1:$dbPort/$restoredDb"
$env:DB_USERNAME = "studhub"
# Задайте DB_PASSWORD своим действующим паролем PostgreSQL, если он отличается от локального значения по умолчанию.
Remove-Item Env:STUDHUB_2FA_KEY -ErrorAction SilentlyContinue
$env:STUDHUB_2FA_KEY_FILE = Join-Path $backup "two-factor.key"
$env:SPRING_JPA_HIBERNATE_DDL_AUTO = "validate"
mvn.cmd spring-boot:run
```

`validate` проверяет совместимость схемы, не меняя её автоматически. До проверки
восстановления не запускайте новую версию приложения с `ddl-auto=update`.

6. Откройте `http://localhost:8080/login`. Проверьте вход, 2FA, курсы, задания,
   проекты, переписки и фотографии. После восстановления старой копии нужно
   сменить пароли/перевыпустить резервные коды, если они менялись после её даты:
   состояние учётных записей и уже использованных резервных кодов также откатывается.
7. Сохраните выбранные настройки подключения и путь к ключу в своём локальном
   способе запуска. Не переносите секреты в код. Сделайте новую проверенную копию.
8. Старую базу удаляйте только после проверки и отдельного решения. Для отката
   переключите `DB_URL` обратно и используйте соответствующий ей ключ.

## Частота и хранение

| Когда | Что делать |
| --- | --- |
| Каждый день работы, перед завершением (ориентир 22:00, Asia/Qyzylorda) | Сделать локальную копию; хранить последние 14 ежедневных |
| Перед обновлением, миграцией, массовым удалением/импортом | Отдельная копия до изменения, независимо от ежедневной |
| Раз в неделю | Перенести проверенную копию на зашифрованный внешний носитель; хранить 8 еженедельных |
| Раз в месяц | Сохранить 6 ежемесячных копий и проверить восстановление |
| После изменения схемы или скриптов копирования | Сразу проверить восстановление |

Пока это регламент ручного запуска: задача Windows и облачное расписание не
установлены. Пропустили день — создайте копию при следующем запуске базы.
Цель для локального проекта — потерять не более одного дня работы. До реального
соблюдения расписания это цель, а не гарантия. Результат сегодняшней проверки
не является обещанием времени восстановления будущей большой базы.

Не храните единственную копию на том же физическом диске, что Docker volume.
Используйте рабочие данные + локальный архив + внешнюю зашифрованную копию;
внешний носитель отключайте после копирования и держите отдельно от ноутбука.
Удаляйте старые архивы вручную только после появления более новых проверенных
копий. Восстановление из 30-дневного архива возвращает данные к его дате.

## Если возникла ошибка

- **Docker/контейнер остановлен:** откройте Docker Desktop, выполните `docker start studhub-db`.
- **Недостаточно места:** освободите место на диске и в Docker, повторите создание новой копии.
- **Ключ не найден:** укажите действующий `-KeyFile`; не генерируйте замену.
- **Checksum mismatch:** копия повреждена/неполна. Возьмите другую проверенную копию, не исправляйте хэш вручную.
- **Target database already exists:** выберите новое `studhub_restore_...`; существующая база не затронута.
- **Версия PostgreSQL отличается:** для этого процесса используйте PostgreSQL 16; обновление версии проверяется отдельно.
- **Source and restore differ:** убедитесь, что исходная база не менялась после создания копии.
- **Ошибка пароля приложения:** проверьте DB_USERNAME/DB_PASSWORD; роли и их пароли не переносятся дампом.

Внутри используются [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)
и [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html). Дамп согласован
на момент снимка PostgreSQL. Владельцы/GRANT не переносятся: объекты принадлежат
роли восстановления. Бинарный архив копируется через `docker cp`, а не через
текстовое перенаправление PowerShell.
